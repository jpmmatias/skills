Lesson 2 · Predict a render

How a state update spreads

You call setCount. What value does your handler see next, how many renders follow, and which components does React call? Three rules answer all three questions.

Why this matters for your mission: almost every “why did this re-render?” question in your app starts with one set call. If you can trace that call through the tree, you can predict a render before you open the Profiler, which is the first milestone of this course.

Rule 1: state is a snapshot

A set function does not change the variable you are holding. It asks React for a new render, and the new value shows up in that next render: “Setting state only changes it for the next render”6. Inside one render, including every event handler created by it, “a state variable’s value never changes”, even in a timeout that fires later6.

Worked example: the +3 button that adds 1

const [number, setNumber] = useState(0);
function handleClick() {
  setNumber(number + 1);   // number is 0 in this render → "replace with 1"
  setNumber(number + 1);   // still 0                    → "replace with 1"
  setNumber(number + 1);   // still 0                    → "replace with 1"
}

Substitute the snapshot value: all three lines say setNumber(0 + 1), so the next render has number === 1, not 36. To build on the pending value instead, pass an updater function. React queues it and, during the next render, runs the queue in order7:

Queue for setNumber(number + 5); setNumber(n => n + 1); starting from 0, as in the docs7
Queued updatePending value passed inResult
“replace with 5”0 (unused)5
n => n + 156

Why does the first row ignore n? Decide before you read on. (A plain value replaces whatever is pending; only a function receives it.)

Rule 2: updates are batched into one render

React “waits until all code in the event handlers has run before processing your state updates”, so several set calls in one handler, even to different state variables or different components, produce one re-render7. Separate intentional events, such as two clicks, are not batched together: each is handled on its own7.

Version note: changed in React 18

Before React 18, only updates inside React event handlers were batched; updates in promises, setTimeout or native event listeners each caused their own render. Since React 18, with the root created by createRoot, all updates are batched automatically no matter where they come from910. flushSync is the opt-out when you must update the screen earlier10. On React 18, an app still mounted with the legacy ReactDOM.render behaves as if it were running React 17, so it does not get automatic batching27; React 19 removed ReactDOM.render, so every React 19 root batches this way15.

Rule 3: a render renders everything inside it

When a component renders, React renders the components it returns, and their children, all the way down1. The memo reference states the default bluntly: “React normally re-renders a component whenever its parent re-renders”11. Props do not have to change. Components above or beside the one that updated are not called at all.

Combine this with lesson 1 and you have the core of the course: many components can render while very few DOM nodes change, because the commit only touches nodes whose output differs1.

Try it: which components render?

The figure models a small app: App holds a theme; Counter holds a count and shows it in Display; List shows three rows. Pick an update. Predict first: how many components will render, and how many DOM nodes will change? Then compare.

function App() {
  const [theme, setTheme] = useState('light');
  return (<>
    <Header theme={theme} />
    <Counter />
    <List items={ITEMS} onPick={id => select(id)} />
  </>);
}
function Counter() {
  const [count, setCount] = useState(0);
  const increment = () => setCount(c => c + 1);
  return (<>
    <Display value={count} />
    <Button label="+1" onClick={increment} />
  </>);
}

With +1, three components render (Counter and the two it returns) and one DOM node changes. With theme, all nine render, yet still one DOM node changes: the header’s class. Eight of those renders produced the same output as before. Whether that is a problem is a question of cost, measured with the Profiler; lesson 3 covers how memo skips such renders and when that is worth it.

One shortcut exists: if you set a state to a value identical to the current one (by Object.is), React skips re-rendering that component and its children, although it may still need to call the component once before skipping the children8.

Milestone challenge · Predict a render

Predict, then profile, one update in your app

Pick one interaction in your own app that updates state (a toggle, typing in a field, selecting a row). Before recording anything, write down which components you expect to render and which DOM nodes you expect to change. Then install React Developer Tools if you have not23, open the Profiler panel, record that one interaction, and select the commit it produced. The flame chart lists the components React rendered in that commit; components that did not render are shown greyed out22 (the panel has changed since that description was written, so say what your version shows).

What to send back

Your written prediction (as it was before you recorded), a screenshot of the Profiler commit, and a short table: component · predicted · observed · rule.

Pass criteria

  1. The prediction names the interaction, at least three components expected to render, and the DOM node(s) expected to change, and was written before the recording.
  2. The table lists every component the Profiler shows as rendered in that commit, each marked as predicted or not.
  3. Every mismatch between prediction and recording is explained by one named rule from lessons 1–2 (own state changed, parent rendered, type/position/key, batching).
  4. At least one component is identified that rendered but whose output was unchanged, with the reason its DOM was left alone.

When you are done, send your work to your teacher in the terminal.
