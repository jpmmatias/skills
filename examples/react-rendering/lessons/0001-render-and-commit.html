Lesson 1 · Predict a render

What “render” means

“It re-rendered” is the most overloaded sentence in React. This lesson pins it down: what React does when it renders, what it does afterwards, and how it decides to keep or throw away what is on screen.

Why this matters for your mission: you cannot predict a re-render until “render” means one precise thing, and most re-render worries disappear once you see that rendering and changing the DOM are different steps.

This course teaches React 19 as documented on react.dev, whose docs were at version 19.3 when the course was written24. Everything in this lesson also holds for React 18.

Five words first

elementA plain object your component returns, describing what to show: “an <h1> with this text”. Not a DOM node.3
renderReact calling your component function to get its elements.1
commitReact changing the real DOM to match the latest render.1
paintThe browser drawing the updated page. Not React’s job.1
reconciliationThe name the legacy docs used (and React’s source still uses) for React comparing the new elements with the previous ones to decide what to keep.4

Rendering is React calling your components

React’s own definition is short: “Rendering” is React calling your components1. Your component is a function; calling it produces elements, which the React docs describe as “a lightweight description of a piece of the user interface”3. Nothing on screen has changed yet when a render finishes.

function Greeting({ name }) {
  return <h1 className="greeting">Hello, {name}</h1>;
}
// Calling it gives a description, roughly:
// { type: 'h1', props: { className: 'greeting', children: ['Hello, ', 'Taylor'] } }

A render is triggered for one of two reasons: it is the component’s initial render, or the state of the component or one of its ancestors was updated1. Rendering is recursive: if the component returns other components, React renders those next, and so on down1. Lesson 2 follows that recursion through a real tree.

One update, four steps

Every screen update in a React app goes through the same sequence: trigger, render, commit, and then the browser paints1. Before you step through it, predict: if a re-render returns exactly what the last render returned, which of these four steps still happen?

The answer to the prediction: the trigger and the render still happen, React still reaches the commit, and the commit has nothing to change. Only the commit ever changes the DOM. The docs describe the render this way: during a re-render React works out which properties changed, but “won’t do anything with that information until the next step, the commit phase”1. In the commit it applies “the minimal necessary operations”, and React only changes the DOM nodes if there’s a difference between renders1. Paint is the browser’s work, not React’s.

Worked example: a clock that never loses your typing

function Clock({ time }) {          // ①
  return (
    <>
      <h1>{time}</h1>               {/* ② */}
      <input />                     {/* ③ */}
    </>
  );
}
// The parent passes a new time string every second.
  1. Trigger: each second the parent’s state changes, so the parent and Clock render again1.
  2. Render: Clock returns an <h1> whose text differs from last time.
  3. Render: it also returns an <input> at the same place, with the same (no) props.
  4. Commit: React updates the <h1> text only. It leaves the <input> alone, so whatever you typed stays1.

Why does ③ survive? Answer before reading on: what would have to be different about line ③ for your typing to be lost? (Hold on to your answer; the next section gives the rule.)

Keep or reset: type, position and key

After each render React compares the new elements with the previous ones, position by position (or by key, when children have keys). The legacy docs called this comparison reconciliation and stated plainly that “the reconciliation algorithm is an implementation detail”4. You do not need its internals*. You need three rules that the current docs state as behaviour2:

Same type, same position

<Counter />
→ <Counter />

Kept. React keeps the component’s state and its DOM, and updates only what changed. “React preserves a component’s state for as long as it’s being rendered at its position in the UI tree.”2

Different type, same position

<div><Counter /></div>
→ <section><Counter /></section>

Reset. A different component (or tag) at a position resets the state of its entire subtree, even the identical Counter inside2.

Different key

<Counter key="taylor" />
→ <Counter key="sarah" />

Reset. A key becomes part of the position, so React sees a different counter and creates its state afresh2.

Two consequences are worth remembering. It is the position in the returned tree that counts, not where the JSX sits in your code: {fancy ? <Counter isFancy /> : <Counter />} keeps its state when fancy flips, because both branches put a Counter at the same place2. And keys must be stable: a key generated during render, such as key={Math.random()}, never matches the previous one, so every item’s component and DOM are recreated on every render, losing any input inside5.

That answers the clock question: the <input> survives because its type and position did not change. Wrap it in a different tag on alternate seconds, or give it a key that changes, and the typing would be lost.

Worked example: resetting a form on purpose

function Chat({ contact }) {
  // Without a key, the draft typed to Alice would still be there after switching to Bob:
  // same component, same position, so the state is kept.
  return <Draft key={contact.id} to={contact} />;   // a new id → a new Draft with empty state
}

The docs use exactly this pattern for a chat app, where keeping the draft would send a message to the wrong person2. Now the faded version: complete it yourself.

Lesson challenge

Keep or reset, in your own app

Find one place in your own app where a value switches what is rendered at one spot: a conditional between two components, a list, a form that shows a different record, or a tab panel. Before you touch the browser, write down whether the state inside (typed text, an open menu, a counter) will be kept or reset when the value switches, and which rule you are using. Then try it.

What to send back

The parent’s JSX at that spot (15 lines at most), your prediction as you wrote it before testing, and what actually happened.

Pass criteria

  1. The snippet shows the element type and the key (or “no key”) of the child at that position, both before and after the switch.
  2. The prediction says “kept” or “reset” and names the rule it relies on: type, position or key.
  3. The observed state before and after the switch is reported (for example the typed text), and any mismatch with the prediction is explained with a corrected rule.

When you are done, send your work to your teacher in the terminal.
