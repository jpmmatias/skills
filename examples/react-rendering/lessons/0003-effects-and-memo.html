Lesson 3 · Diagnose with evidence

Effects, Strict Mode and memoization

Three things make React look busier than it is: effects that seem to run at odd moments, development-only double calls, and renders that change nothing. This lesson separates real costs from false alarms, and shows when memo, useMemo and useCallback actually skip work.

Why this matters for your mission: the second milestone asks you to explain a surprising re-render or effect run from evidence and pick the fix the evidence supports. Most wrong fixes come from one of the three false alarms above.

Effects run after the commit

An Effect is code that runs because the component was displayed, to synchronise with something outside React. The docs place it precisely: “Effects run at the end of a commit after the screen updates”12. So the render you learned about in lessons 1–2 is already over, and the DOM is already updated, when your Effect starts. Predict before stepping through: does the Effect come before or after the browser paints?

The answer is “usually after, but do not count on it”. If an Effect was not caused by an interaction, React “will generally let the browser paint the updated screen first”; if it was caused by an interaction such as a click, React “may run your Effect before the browser paints”13. What you can rely on is that the Effect runs after the commit. One consequence matters for performance: an Effect that immediately sets state starts the whole trigger → render → commit sequence again, which is why the docs recommend computing derived values during rendering instead20.

Strict Mode: double calls on purpose, in development only

If you see a component log twice or an Effect connect, disconnect and connect again, check whether you are in development with <StrictMode> on before you call it a bug. Strict Mode repeats certain calls to expose impure rendering and missing cleanup, and “all of these checks are development-only and do not impact the production build”14.

The right reaction to an Effect firing twice is not a useRef guard but a cleanup: “The right question isn’t ‘how to run an Effect once’, but ‘how to fix my Effect so that it works after remounting’”12. With a correct cleanup, the user cannot tell setup → cleanup → setup from a single setup.

Version note: React 18 → 19

The Effect double-run on mount arrived with React 18, as a new development-only Strict Mode check9. React 19 changed two details: during the development double render, useMemo and useCallback reuse the memoized results from the first render, and ref callbacks are double-invoked on the initial mount15. If your team is on 18, the ref-callback row above may not apply.

A re-render is not a DOM update

Lesson 1’s rule is the most useful sentence in any performance discussion: React only changes the DOM where the output differs1. A component that “re-renders 40 times” may have touched the DOM zero times. The cost of a wasted render is the time spent calling it and its children, so the question is always how long, which the Profiler measures (its actualDuration counts milliseconds spent rendering a subtree in one update21).

When memoization skips work

memo(Component) lets React skip re-rendering a child when its parent re-renders, if every prop is equal by Object.is to last time. It never stops a re-render caused by the component’s own state or by a context it reads, and the docs call it “a performance optimization, not a guarantee”11. Its weak spot is identity: an object or function created during render is a new value every time, which makes memo “completely useless”11. That is what useCallback (for functions) and useMemo (for values) are for: keeping the same identity across renders until a dependency changes1716.

Worked example: memo that does nothing

const List = memo(function List({ items, onPick }) { … });

function App() {
  const [theme, setTheme] = useState('light');
  // ↓ a new function on every App render
  return <List items={ITEMS} onPick={id => select(id)} />;
}

ITEMS is a module-level constant, so it is equal every time; onPick is not. Every App render passes a new function, memo sees a changed prop, and List renders anyway, along with every row. Why does the arrow function count as changed when its code is identical? Answer for yourself, then try it below: turn on memo for List alone, toggle the theme, and watch List still render.

When is it worth it?

The reference pages give the same short list for all three tools161711:

  1. memo helps when a component re-renders often with the same props and its rendering is expensive. If there is no perceptible lag, it is unnecessary.
  2. useCallback / useMemo help when the value goes to a memo component, or is a dependency of another Hook (such as an Effect that should not re-run).
  3. useMemo also helps for a calculation that is noticeably slow and whose inputs rarely change. Measure it: wrap it in console.time; the docs suggest about 1 ms or more as worth memoizing, tested with CPU throttling because your machine is faster than your users’16.

Outside those cases there is “no benefit”, and also “no significant harm”, apart from less readable code16.

Status note: React Compiler (checked November 2026)

React Compiler reached its first stable release, 1.0, on October 7, 202519. It is a build-time tool you opt into (mainly a Babel plugin), not part of the React runtime, and it works with React 17 and up1819. It automatically applies the equivalent of memo, useMemo and useCallback to components and hooks (not to every function), which is exactly the “skip renders with equal inputs” idea above, done for you18. useMemo and useCallback remain as escape hatches, and for existing code the docs advise leaving existing memoization in place or testing carefully before removing it18. The compiler changes which renders happen, not the rules of this course: renders, commits and Effects work as taught. Check your build config to know whether it is on in your app.

Milestone challenge · Diagnose with evidence

One surprising render, explained and fixed (or left alone)

In your own app, find one component that renders more often than you expect, or one Effect that runs more often than you expect. Record the interaction in the React DevTools Profiler, decide on the cause using the rules from this course, make at most one change, and record the same interaction again. “No change, because it is cheap” is a valid outcome if the numbers support it.

What to send back

Two Profiler screenshots or exports (before and after) of the same interaction, the diff of your one change (or the measurement that justified no change), and a three-sentence explanation: what rendered or ran, why, and what the change did.

Pass criteria

  1. The before recording names the target component or Effect and shows how many commits it rendered (or ran) in, for one named interaction.
  2. The explanation names one cause from the course (own state, parent rendered, a new function or object prop, an Effect setting state, or Strict Mode in development) and points to the line of code it comes from.
  3. The after recording of the same interaction shows the target rendering (or running) in fewer commits, or, for “no change”, the before recording shows the target’s render time in milliseconds next to the threshold you used.
  4. If the cause was Strict Mode, the claim is backed by a production build run, or by the setup → cleanup → setup pattern in the console.

When you are done, send your work to your teacher in the terminal.
