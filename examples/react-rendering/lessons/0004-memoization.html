Lesson 4 · Diagnose with evidence

When memoization skips work

A render that changes nothing on screen is not automatically a problem, and memo, useMemo and useCallback do nothing at all when one prop is new on every render. This lesson shows when they actually skip work, and how to tell from evidence whether that matters.

Why this matters for your mission: “pick the fix the evidence supports” usually comes down to one question: will this memoization skip anything, and is what it skips worth the extra code?

A re-render is not a DOM update

Lesson 1’s rule is the most useful sentence in any performance discussion: React only changes the DOM where the output differs1. A component that “re-renders 40 times” may have touched the DOM zero times. The cost of a wasted render is the time spent calling it and its children, so the question is always how long, which the Profiler measures (its actualDuration counts milliseconds spent rendering a subtree in one update21).

What memo compares

memo(Component) lets React skip re-rendering a child when its parent re-renders, if every prop is equal by Object.is to last time. It never stops a re-render caused by the component’s own state or by a context it reads, and the docs call it “a performance optimization, not a guarantee”11. Its weak spot is identity: an object or function created during render is a new value every time, which makes memo “completely useless”11. That is what useCallback (for functions) and useMemo (for values) are for: keeping the same identity across renders until a dependency changes1716.

This lesson assumes React Compiler is off, as do the practice items and the model below. With the compiler on, two of these predictions change; the box at the end of the lesson says which, and how to check your app.

Worked example: memo that does nothing

const List = memo(function List({ items, onPick }) { … });

function App() {
  const [theme, setTheme] = useState('light');
  // ↓ a new function on every App render
  return <List items={ITEMS} onPick={id => select(id)} />;
}

ITEMS is a module-level constant, so it is equal every time; onPick is not. Every App render passes a new function, memo sees a changed prop, and List renders anyway, along with every row. Why does the arrow function count as changed when its code is identical? Answer for yourself, then try it below: turn on memo for List alone, toggle the theme, and see whether List renders.

When is it worth it?

The reference pages give short, overlapping lists161711:

  1. memo helps when a component re-renders often with the same props and its rendering is expensive. If there is no perceptible lag, it is unnecessary.
  2. useCallback / useMemo help when the value goes to a memo component, or is a dependency of another Hook (such as an Effect that should not re-run).
  3. useMemo also helps for a calculation that is noticeably slow and whose inputs rarely change. Measure it: wrap it in console.time; the docs suggest about 1 ms or more as worth memoizing, tested with CPU throttling because your machine is faster than your users’16.

Outside those cases there is “no benefit”, and also “no significant harm”, apart from less readable code16. Remember lesson 2’s exception too: JSX a wrapper receives as children is not re-rendered when only the wrapper’s state changes11, which often removes the need for memo altogether.

Status note: React Compiler (checked November 2026)

React Compiler reached its first stable release, 1.0, on October 7, 202519. It is a build-time tool (mainly a Babel plugin), not part of the React runtime, and it works with React 17 and up1819. It is optional, but new projects can start with it on: Expo SDK 54 and up enables it by default, and create-vite and create-next-app offer templates with it enabled19. It automatically applies the equivalent of memo, useMemo and useCallback to components and hooks (not to every function); useMemo and useCallback remain as escape hatches, and for existing code the docs advise leaving existing memoization in place or testing carefully before removing it18.

With the compiler on, renders, commits and Effects still work as taught, but two predictions change: objects and functions created in a component are cached between renders instead of being new every time, and a child whose props did not change is usually skipped without memo18. The practice items and the render model in this course assume the compiler is off. To check your app, look in React DevTools: components the compiler optimized show a “Memo ✨” badge28.

Milestone challenge · Diagnose with evidence

One surprising render, explained and fixed (or left alone)

In your own app, find one component that renders more often than you expect, or one Effect that runs more often than you expect. Collect evidence for one interaction: for a component, record it in the React DevTools Profiler (or the React Performance tracks of your browser’s Performance panel, React 19.2+ in development2930); for an Effect, count how many times a console.log in its setup prints. Decide on the cause using the rules from this course, make at most one change, and collect the same evidence again. “No change, because it is cheap” is a valid outcome if the numbers support it. If the Components panel shows a “Memo ✨” badge next to your components, React Compiler is on: say so, because it skips renders that rules 1–3 predict1828.

What to send back

The before and after evidence (Profiler screenshots or exports, or the two console logs), the diff of your one change (or the measurement that justified no change), and a three-sentence explanation: what rendered or ran, why, and what the change did.

Pass criteria

  1. The before evidence names one interaction and the target: for a component, the number of commits in which the Profiler shows it rendered; for an Effect, the number of times the console.log in its setup prints.
  2. The explanation names one cause from the course (own state, parent rendered, a new function or object prop, an Effect setting state, or Strict Mode in development) and points to the line of code it comes from.
  3. The after evidence for the same interaction, collected the same way, shows a lower count, or, for “no change”, the before recording shows the target’s render time in milliseconds next to the threshold you used.
  4. If the cause was Strict Mode, the claim is backed by the same count in a production build, or by the setup → cleanup → setup pattern in the console (the Profiler shows one commit either way).

When you are done, send your work to your teacher in the terminal.
