Lesson 3 · Diagnose with evidence

Effects and Strict Mode

Two things make React look busier than it is: Effects that seem to run at odd moments, and development-only double calls. This lesson places Effects in the update sequence and separates Strict Mode’s deliberate repeats from real bugs.

Why this matters for your mission: the second milestone asks you to explain a surprising re-render or Effect run from evidence. Before you can blame a component, you need to know when its Effects run, and which repeats only happen on your development machine.

Effects run after the commit

An Effect is code that runs because the component was displayed, to synchronise with something outside React20. The docs place it precisely: “Effects run at the end of a commit after the screen updates”12. So the render you met in lessons 1–2 is already over, and the DOM is already updated, when your Effect starts. Predict before stepping through: after a click, can your Effect run before the browser paints?

The answer is yes: the drawing shows the usual order, but it is not guaranteed. If an Effect was not caused by an interaction, React “will generally let the browser paint the updated screen first”; if it was caused by an interaction such as a click, React “may run your Effect before the browser paints”13. What you can rely on is that the Effect runs after the commit.

If an Effect must finish before the user sees the screen, for example measuring and positioning a tooltip so it does not flicker, the docs point to useLayoutEffect, which blocks the paint, and add that this “shouldn’t be needed for the vast majority of Effects”13.

Worked example: the Effect that costs a second render

function Profile({ first, last }) {
  const [fullName, setFullName] = useState('');
  useEffect(() => {
    setFullName(first + ' ' + last);   // ① runs after the commit
  }, [first, last]);
  return <h1>{fullName}</h1>;           // ② first commit shows ''
}
  1. The first render returns an empty heading, React commits it, and only then does the Effect run.
  2. The Effect’s set call triggers a whole new render and commit. The docs describe this as restarting “the whole process from scratch”20.

The fix the docs give is to compute it during rendering: const fullName = first + ' ' + last;20. Why does line ① exist at all, if the value can be computed in the render? Answer for yourself: what is outside React here that needs synchronising?

Strict Mode: double calls on purpose, in development only

If you see a component log twice or an Effect connect, disconnect and connect again, check whether you are in development with <StrictMode> on before you call it a bug. Strict Mode repeats certain calls to expose impure rendering and missing cleanup, and “all of these checks are development-only and do not impact the production build”14.

What runs, with Strict Mode on, in React 19
CodeDevelopment (Strict Mode)Production build
Component body (top-level code)called twice, on every render14called once
Event handlersnot repeated14run when the event fires
useEffect on the first mountsetup → cleanup → setup12setup once
Ref callbacks on the first mountsetup → cleanup → setup14once

The right reaction to an Effect firing twice is not a useRef guard but a cleanup: “The right question isn’t ‘how to run an Effect once’, but ‘how to fix my Effect so that it works after remounting’”12. With a correct cleanup, the user cannot tell setup → cleanup → setup from a single setup.

Version note: React 18 → 19

The Effect double-run on mount arrived with React 18, as a new development-only Strict Mode check9. React 19 changed two details: during the development double render, useMemo and useCallback reuse the memoized results from the first render, and ref callbacks are double-invoked on the initial mount15. If your team is on React 18, the ref-callback row does not apply: the double call of ref callbacks is one of the React 19 changes15.

One more, from lesson 2: Effects see a snapshot of state, just like event handlers.

Lesson challenge

One Effect, two builds

Pick one Effect in your own app that sets something up: a subscription, a timer, a listener or a fetch. Add a console.log at the start of its setup and one in its cleanup (add a cleanup if it has none, and say so). Mount the component in development with Strict Mode on, then in a production build, and copy both console sequences.

What to send back

The Effect’s code with the two log lines and its dependency array, the two console sequences, and one sentence per extra line in the development sequence.

Pass criteria

  1. The code shows the setup log, the cleanup log and the dependency array (or “no array”).
  2. Two console sequences for the same mount are included, one labelled development (Strict Mode) and one labelled production build.
  3. Each line that appears only in the development sequence is attributed to a named cause (Strict Mode remount, or a dependency change), and the answer states whether the cleanup undoes what the setup started.

When you are done, send your work to your teacher in the terminal.
