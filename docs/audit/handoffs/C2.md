## Decisions

1. **No entrance animations.**
   - Bars no longer grow when scrolled into view. A grow-in is decoration (Höffler & Leutner), and it is what made the check capture wrong frames.
   - Motion is reserved for state changes the learner triggers.
2. **Steppers start on step 1; flows start on an "Overview" poster.**
   - Segmenting favours one change at a time for hand-drawn steppers, so they start on step 1.
   - Flows dim instead of hiding, so their poster can be the whole graph. "Overview" is an explicit last chapter.
   - Next/chapter buttons play only that chapter (`segment`). Play runs continuously. Back jumps without animating.
3. **Visibility is watched in `viz.js` (`Learncraft.viz.watch`) rather than through `Learncraft.observeVisibility`.**
   - C1's version uses `isIntersecting` with `threshold: 0.25`, which stays `true` down to a 1 px sliver, so it pauses only when the element is fully off-screen.
   - If C1 switches it to `intersectionRatio >= 0.25`, `viz.js` can call it instead.
4. **The phone scene layout uses a crop, not scaled fonts.**
   - The stage keeps its 960×540 coordinates. Below 480 px the `viewBox` becomes `def.phone.focus`, or else the SVG bounding box plus room for the title.
   - Terminals move under the stage. This needs no change to existing scenes.
   - Scenes whose mechanism is wider than about 480 units should declare `phone.focus`.
5. **Practice recording falls back in this order:** `ctx.record` → `Learncraft.recordPractice` → `window.Progress.record`. The last is what C1's `practice.js` provides today.
6. **The threshold explorer keeps its original Park–Miller generator,** so existing lessons keep their data and right answer. Everything new uses `Learncraft.rng`.
7. **`.fade` handling was removed from `diagram.js`.** C1's `practice.js` owns it.

## Known limitations

- `viz.js` is 413 lines, slightly over the ~400 target, mostly header documentation and the i18n table.
- Narration resumes at the next chapter after a pause, not mid-sentence. `speechSynthesis.pause` is unreliable in Chrome.

## Motion guidelines

- **When to animate:**
  - Only when the motion is the concept: a packet crossing a hop, a pointer moving, a distribution shifting, a value landing in a zone.
  - Never on scroll-in, never for emphasis alone.
  - If the insight comes from changing a value, build an explorable instead.
- **Who starts it:**
  - The learner always does.
  - Next or a chapter button plays one chapter or segment and stops. Play runs on, and pauses itself off-screen and on hidden tabs.
- **Durations:**
  - Transitions on a learner action: 0.5–0.6 s.
  - One step's motion: ≤ 1.1–1.8 s inside a 2.2–2.6 s step, which leaves reading time.
  - Whole scenes: ≤ ~20 s of motion in 3–6 chapters.
- **Easing:** `ease` (cubic in-out) for things that travel (packets, pointers, scene beats). `easeOut` for value changes that settle (bars, markers). No bounce or overshoot.
- **State:** every view is a pure function of time or of its parameters (`onSeek(t)`, `render(values, rng)`), so scrub, back, print, reduced motion and screenshots all agree.
- **Poster:** the first paint and the print frame must be a true, complete picture. That is the final frame, or step 1 for segmented steppers.
- **Reduced motion:**
  - Same content, no tweens.
  - Play becomes "Next chapter".
  - Beats jump to their end state, and no packets are drawn.
  - No rAF loops run.
- **Phone:**
  - Lay generated SVG out at the container width, so 12–13 px stays 12–13 px.
  - For scenes, keep the mechanism within about 480 units or declare `phone.focus`, and put text in terminals or captions, not tiny SVG labels.
  - Check that text renders at ≥ 11 px at 390 px.
- **Data:** numbers on screen are either derived from the data shown (binary search), simulated with a seed and labelled "simulated", or labelled "illustrative". Never write "real data" without a source id.
